Dart Exceções Próprias

Com o throw você já lança Exception('Saldo insuficiente'). Funciona, mas tem dois problemas: quem pega a exceção só recebe um texto (e se quiser saber quanto faltou?), e não dá para escrever um on só para "saldo insuficiente", porque toda Exception('…') é do mesmo tipo. A solução é criar o seu próprio tipo de exceção: uma classe com um nome que diz o problema e campos com os detalhes.

Você vai aprender
  • Como criar uma exceção própria: class SaldoInsuficienteException implements Exception.
  • Por que ela aparece como Instance of '…', e como o toString dá a ela uma mensagem.
  • Como guardar os detalhes do problema em campos e usá-los no catch.
  • Como montar uma família de exceções e pegar todas de uma vez com um on só.
  • Os erros reais: extends Exception e a classe que esqueceu o implements Exception.

Esta aula usa classes, construtores, @override e herança. Todos os programas rodaram no Dart SDK 3.13.5 da máquina da Ana (usuária ana, computador notebook), com dart run arquivo.dart.

A ideia: o formulário de reclamação

Na padaria, quando algo dá errado com um pedido, a Ana não escreve só "deu problema" num papel. Ela preenche um formulário de reclamação com o tipo do problema marcado ("produto em falta", "pagamento recusado") e os detalhes: qual produto, quantos faltaram. Com o formulário, o gerente sabe na hora quem resolve e o que fazer.

Uma exceção própria é esse formulário:

  • o nome da classe é o tipo do problema (SaldoInsuficienteException), e é por ele que o on separa os casos;
  • os campos são os detalhes (pedido, saldo);
  • o toString é o resumo escrito que aparece quando alguém mostra a exceção.

1. A primeira exceção própria

class SaldoInsuficienteException implements Exception {
  final int pedido;
  final int saldo;

  SaldoInsuficienteException(this.pedido, this.saldo);
}

void main() {
  throw SaldoInsuficienteException(500, 70);
}

2. toString: a mensagem da exceção

Quando o Dart precisa mostrar um objeto como texto (num print, num $e, no Unhandled exception), ele chama o método toString() do objeto (veja toString, == e hashCode). Escrevendo o seu, você decide a mensagem. E dá para acrescentar o que mais quiser, como um get que calcula quanto falta:

class SaldoInsuficienteException implements Exception {
  final int pedido;
  final int saldo;

  SaldoInsuficienteException(this.pedido, this.saldo);

  int get falta => pedido - saldo;

  @override
  String toString() =>
      'SaldoInsuficienteException: pediu R\$ $pedido, tem R\$ $saldo';
}

var saldo = 70;

void sacar(int valor) {
  if (valor > saldo) {
    throw SaldoInsuficienteException(valor, saldo);
  }
  saldo -= valor;
  print('Saque de R\$ $valor. Saldo: R\$ $saldo');
}

void main() {
  for (final pedido in [20, 500]) {
    try {
      sacar(pedido);
    } on SaldoInsuficienteException catch (e) {
      print('Recusado: $e');
      print('Faltam R\$ ${e.falta}.');
    }
  }
  sacar(90);
}
int get falta => pedido - saldo;
Um getter: quem pegar a exceção pode perguntar e.falta.
@override String toString() => '…';
Troca o Instance of '…' por uma mensagem útil. Começar com o nome do tipo (SaldoInsuficienteException: ) imita as exceções do próprio Dart.
on SaldoInsuficienteException catch (e)
Pega só este tipo. Como o Dart sabe o tipo de e, dá para usar os campos e o getter: e.falta, e.pedido.
sacar(90);
Fora do try, de propósito, para ver como fica a exceção não tratada.

3. Uma família de exceções

A padaria tem vários problemas possíveis num pedido: o produto não existe, o estoque não dá. Às vezes você quer tratar cada um de um jeito; às vezes quer só dizer "pedido recusado" para todos. Para os dois casos, crie uma classe-mãe para a família e uma filha para cada problema:

abstract class PedidoException implements Exception {
  final String mensagem;
  PedidoException(this.mensagem);

  @override
  String toString() => '$runtimeType: $mensagem';
}

class ProdutoNaoEncontrado extends PedidoException {
  ProdutoNaoEncontrado(String produto) : super('não temos "$produto"');
}

class EstoqueInsuficiente extends PedidoException {
  final int faltam;
  EstoqueInsuficiente(String produto, this.faltam)
      : super('faltam $faltam de "$produto"');
}

final estoque = {'pão': 30, 'bolo': 2};

void vender(String produto, int qtd) {
  final tem = estoque[produto];
  if (tem == null) {
    throw ProdutoNaoEncontrado(produto);
  }
  if (qtd > tem) {
    throw EstoqueInsuficiente(produto, qtd - tem);
  }
  estoque[produto] = tem - qtd;
  print('Vendeu $qtd $produto');
}

void main() {
  final pedidos = [('pão', 10), ('pizza', 1), ('bolo', 5)];
  for (final (produto, qtd) in pedidos) {
    try {
      vender(produto, qtd);
    } on EstoqueInsuficiente catch (e) {
      print('Encomendar ${e.faltam}: $e');
    } on PedidoException catch (e) {
      print('Pedido recusado: $e');
    }
  }
  print(estoque);
}
abstract class PedidoException implements Exception
A mãe da família. É abstrata: ninguém lança uma PedidoException "genérica", só as filhas. O toString dela usa o runtimeType (o nome da classe filha) e a mensagem, e vale para todas as filhas.
class ProdutoNaoEncontrado extends PedidoException
Uma filha (veja Herança). O : super('…') passa a mensagem pronta para o construtor da mãe.
class EstoqueInsuficiente … final int faltam;
Outra filha, com um detalhe a mais: quantos faltam.
on EstoqueInsuficiente … on PedidoException
O primeiro on trata o caso específico (e usa o e.faltam). O segundo pega qualquer outra exceção da família. A ordem importa: do mais específico para o mais geral.
for (final (produto, qtd) in pedidos)
Cada pedido é um record com o produto e a quantidade, desmontado direto no for (veja Patterns).
$ dart run p3.dart
Vendeu 10 pão
Pedido recusado: ProdutoNaoEncontrado: não temos "pizza"
Encomendar 3: EstoqueInsuficiente: faltam 3 de "bolo"
{pão: 20, bolo: 2}

A pizza caiu no on PedidoException (não havia um on só para ProdutoNaoEncontrado, mas ela é da família). O bolo caiu no on EstoqueInsuficiente, que veio antes. O estoque do bolo não mudou, porque o throw parou a venda.

Formas diferentes de fazer a mesma coisa

Com uma família sealed (selada: todas as filhas ficam no mesmo arquivo), o Dart sabe quais são todas as exceções da família. Aí você pega a mãe com um on só e trata cada filha numa expressão switch, e o Dart reclama se você esquecer alguma:

sealed class PagamentoException implements Exception {}

class CartaoRecusado extends PagamentoException {
  final String motivo;
  CartaoRecusado(this.motivo);
}

class PixExpirado extends PagamentoException {
  final int minutos;
  PixExpirado(this.minutos);
}

String explicar(PagamentoException e) => switch (e) {
      CartaoRecusado(:final motivo) => 'Cartão recusado: $motivo',
      PixExpirado(:final minutos) => 'O Pix expirou depois de $minutos minutos',
    };

void pagar(int caso) {
  if (caso == 1) throw CartaoRecusado('sem limite');
  if (caso == 2) throw PixExpirado(30);
  print('Pago!');
}

void main() {
  for (final caso in [0, 1, 2]) {
    try {
      pagar(caso);
    } on PagamentoException catch (e) {
      print(explicar(e));
    }
  }
}

$ dart run selada.dart
Pago!
Cartão recusado: sem limite
O Pix expirou depois de 30 minutos
SituaçãoQual usar
Um problema simples, que ninguém vai tratar de um jeito especialthrow Exception('motivo') ou StateError/ArgumentError (aula throw)
Quem chama precisa reconhecer o problema ou usar os detalhesUma classe … implements Exception com campos e toString

Quando dá errado

Escreveu extends Exception 
class SaldoInsuficienteException extends Exception {
  final int falta;
  SaldoInsuficienteException(this.falta);
}

void main() {
  throw SaldoInsuficienteException(30);
}

$ dart run p5.dart
p5.dart:1:42: Error: The class 'Exception' can't be extended outside of its library because it's an interface class.
class SaldoInsuficienteException extends Exception {
                                         ^
p5.dart:3:3: Error: The superclass, 'Exception', has no unnamed constructor that takes no arguments.
  SaldoInsuficienteException(this.falta);
  ^^^^^^^^^^^^^^^^^^^^^^^^^^

Duas mensagens:

The class 'Exception' can't be extended outside of its library because it's an interface class.
"A classe Exception não pode ser estendida fora da biblioteca dela, porque é uma interface class." No Dart 3, Exception é marcada como interface (veja sealed, final, base e interface): de fora, só dá para implementá-la, nunca herdar dela.
The superclass, 'Exception', has no unnamed constructor that takes no arguments.
"A superclasse Exception não tem um construtor sem nome e sem argumentos" para o seu construtor chamar. É consequência da primeira.

Como consertar: troque extends por implements: class SaldoInsuficienteException implements Exception.

Esqueceu o implements Exception 
class SaldoInsuficiente {
  final int falta;
  SaldoInsuficiente(this.falta);
}

void main() {
  try {
    throw SaldoInsuficiente(30);
  } on Exception catch (e) {
    print('Tratado: $e');
  }
  print('Fim');
}

$ dart run p4.dart
Unhandled exception:
Instance of 'SaldoInsuficiente'
#0      main (file:///home/ana/p4.dart:8:5)
#1      _delayEntrypointInvocation.<anonymous closure> (dart:isolate-patch/isolate_patch.dart:313:19)
#2      _RawReceivePort._handleMessage (dart:isolate-patch/isolate_patch.dart:192:12)

O Dart deixa lançar qualquer objeto, então compilou. Mas a classe não diz que é uma Exception, e o on Exception não a reconheceu: ela passou direto, e nem o Fim apareceu. Como consertar: class SaldoInsuficiente implements Exception (e, de quebra, um nome terminado em Exception e um toString).

A mensagem saiu Instance of '…'

Você já viu na seção 1: sem toString, o print e o Unhandled exception mostram só Instance of 'SaldoInsuficienteException'. Não é erro do Dart, é a mensagem padrão de qualquer objeto. Como consertar: escreva o @override String toString() => '…';.

Missão final: a nota inválida

Missão: siga os três comentários. (1) Crie a classe NotaInvalidaException implements Exception, com um campo final int nota, o construtor e um toString que devolva 'Nota inválida: $nota (vai de 0 a 10)'. (2) Lance NotaInvalidaException(nota) no lugar da Exception. (3) Troque o on Exception por on NotaInvalidaException.

// 1. crie aqui a classe NotaInvalidaException

void registrar(int nota) {
  if (nota < 0 || nota > 10) {
    throw Exception('nota fora da faixa'); // 2. lance a sua exceção
  }
  print('Registrada: $nota');
}

void main() {
  for (final nota in [7, 12]) {
    try {
      registrar(nota);
    } on Exception catch (e) { // 3. pegue só a sua exceção
      print('$e');
    }
  }
}

class NotaInvalidaException implements Exception {
  final int nota;
  NotaInvalidaException(this.nota);

  @override
  String toString() => 'Nota inválida: $nota (vai de 0 a 10)';
}

void registrar(int nota) {
  if (nota < 0 || nota > 10) {
    throw NotaInvalidaException(nota);
  }
  print('Registrada: $nota');
}

void main() {
  for (final nota in [7, 12]) {
    try {
      registrar(nota);
    } on NotaInvalidaException catch (e) {
      print('$e');
    }
  }
}

No lab, a solução mostrou Registrada: 7 e Nota inválida: 12 (vai de 0 a 10).

Resumo

  • Uma exceção própria é uma classe com implements Exception. O nome diz o problema; por costume, termina em Exception.
  • Campos guardam os detalhes; quem pega com on SeuTipo catch (e) pode usá-los (e.falta).
  • Sem toString, a mensagem é Instance of '…'; com ele, você escolhe o texto.
  • Uma classe-mãe (abstract ou sealed) agrupa várias exceções: um on da mãe pega todas as filhas. Ponha os on do mais específico para o mais geral.
  • No Dart 3, extends Exception não compila: use implements Exception.
