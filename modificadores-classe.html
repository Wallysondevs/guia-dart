Dart sealed, final, base e interface

Nas aulas anteriores, qualquer classe podia ser estendida (extends) e implementada (implements) por qualquer outra. Às vezes, quem escreve uma classe quer pôr regras: "a conta bancária ninguém estende, para não driblar a conferência do depósito"; "as formas de pagamento são estas quatro e pronto". Para isso, o Dart 3.0 trouxe os modificadores de classe, palavras que vão antes de class: sealed, final, base e interface.

Você vai aprender
  • O que é uma biblioteca no Dart (spoiler: cada arquivo) e por que as regras valem "fora da biblioteca".
  • sealed: uma família fechada de subclasses, e o switch que confere se você tratou todas.
  • final: ninguém de fora estende nem implementa.
  • interface: de fora, só implementa; base: de fora, só estende.
  • A tabela do que cada modificador permite, e os erros reais de cada regra quebrada.

Todos os programas desta aula rodaram no Dart 3.13.5 da máquina da Ana (usuária ana, computador notebook), com dart run arquivo.dart. Os modificadores existem desde o Dart 3.0. Esta aula usa dois arquivos por programa e o import (o assunto completo está em import, export e Bibliotecas).

A ideia: as regras valem para quem é de fora

Pense na cozinha da padaria. Lá dentro, a equipe mexe em tudo: abre o forno, muda a receita. Para quem é de fora, há regras na porta: "clientes não entram", "fornecedores só até a despensa". As regras não são para a equipe; são para os de fora.

No Dart, a "cozinha" é a biblioteca: cada arquivo .dart é uma biblioteca. Quem está no mesmo arquivo da classe pode tudo; os modificadores restringem o que outros arquivos (que fazem import) podem fazer com ela. É a mesma ideia da privacidade com _, que também vale por arquivo.

Dá para combinar abstract com base, interface ou final (por exemplo, abstract interface class, que é a "interface pura" de outras linguagens). O sealed já é abstrato por natureza. E o mixin class você viu em Mixins.

1. sealed: uma família fechada

Na lojinha, as formas de pagamento são Pix, cartão e dinheiro. Cada uma tem dados diferentes: o Pix tem a chave, o cartão tem as parcelas, o dinheiro tem quanto o cliente entregou. A Ana quer que o Dart saiba que só existem essas três. Esse é o trabalho do sealed ("selado", "lacrado"). Primeiro, o arquivo da biblioteca:

sealed class Pagamento {
  final double valor;

  Pagamento(this.valor);
}

class Pix extends Pagamento {
  final String chave;

  Pix(super.valor, this.chave);
}

class Cartao extends Pagamento {
  final int parcelas;

  Cartao(super.valor, this.parcelas);
}

class Dinheiro extends Pagamento {
  final double recebido;

  Dinheiro(super.valor, this.recebido);
}

Agora o programa, em outro arquivo, que usa a família:

import 'pagamentos.dart';

String resumo(Pagamento p) {
  return switch (p) {
    Pix pix => 'Pix de R\$ ${pix.valor} para ${pix.chave}',
    Cartao c => 'Cartão: R\$ ${c.valor} em ${c.parcelas}x',
    Dinheiro d => 'Dinheiro: troco de R\$ ${d.recebido - d.valor}',
  };
}

void main() {
  final pagamentos = [
    Pix(25.0, 'ana@lojinha'),
    Cartao(120.0, 3),
    Dinheiro(17.5, 20.0),
  ];
  for (final p in pagamentos) {
    print(resumo(p));
  }
}
sealed class Pagamento
A mãe da família. Ela é automaticamente abstrata (não dá para criar um Pagamento puro) e só pode ter filhas dentro do mesmo arquivo.
class Pix extends Pagamento
As filhas, no mesmo arquivo. Elas são classes comuns: podem ser criadas, e até estendidas por outros arquivos. Só a mãe é lacrada.
import 'pagamentos.dart';
O caixa.dart traz para si as classes do outro arquivo (que está na mesma pasta).
switch (p) { Pix pix => …, … }
Uma expressão switch (veja switch). Pix pix é um padrão que quer dizer "se p for um Pix, chame-o de pix neste caso", e então pix.chave funciona (veja Patterns).
(sem _ no fim)
Como a família é lacrada, o Dart sabe que só existem Pix, Cartao e Dinheiro, e que os três casos cobrem tudo.
$ dart run caixa.dart
Pix de R$ 25.0 para ana@lojinha
Cartão: R$ 120.0 em 3x
Dinheiro: troco de R$ 2.5

É o mesmo poder do switch com enums, mas com a vantagem de que cada opção tem os seus próprios dados. Se a Ana acrescentar Boleto à família, todo switch que esqueceu o boleto para de compilar e aponta a falta. Experimente:

2. final: ninguém de fora mexe

A conta da lojinha recusa depósito negativo. Se outro arquivo pudesse estender a conta e sobrescrever o depositar, a conferência seria driblada. Com final class, de fora ninguém estende nem implementa:

final class Conta {
  double saldo = 0;

  void depositar(double valor) {
    if (valor <= 0) {
      print('Depósito recusado: R\$ $valor');
      return;
    }
    saldo += valor;
  }
}

interface class Impressora {
  void imprimir(String texto) => print('[impressora] $texto');
}

base class Funcionario {
  final String nome;

  Funcionario(this.nome);

  String cracha() => 'Funcionário: $nome';
}

final class Poupanca extends Conta {}

import 'banco.dart';

void main() {
  final c = Conta();
  c.depositar(50);
  c.depositar(-10);
  print('Saldo: R\$ ${c.saldo}');
  final p = Poupanca();
  p.depositar(30);
  print('Poupança: R\$ ${p.saldo}');
}

$ dart run final_ok.dart
Depósito recusado: R$ -10.0
Saldo: R$ 50.0
Poupança: R$ 30.0
  • De fora, usar a conta é normal: criar, depositar, ler o saldo. O final só proíbe estender e implementar.
  • Dentro do banco.dart, a Poupanca estendeu a Conta: na "cozinha" pode. Mas repare que ela também é final class. Se não fosse, o Dart reclamaria (veja Quando dá errado): a filha de uma classe final tem de ser final, base ou sealed, para a porta não ficar aberta pelos fundos.
Não confunda com a variável final

final preco = 10; (veja final e const) é uma variável que não muda de valor. final class Conta é uma classe que ninguém de fora estende nem implementa. A palavra é a mesma; os assuntos são diferentes.

3. interface e base: meio aberto

interface class: de fora, só implements

A Impressora do banco.dart é uma interface class. Outro arquivo pode criar impressoras e pode implementar a interface (por exemplo, uma impressora de teste), mas não pode herdar o código dela:

import 'banco.dart';

class ImpressoraDeTeste implements Impressora {
  @override
  void imprimir(String texto) => print('[teste] $texto');
}

void main() {
  Impressora().imprimir('Cupom 001');
  ImpressoraDeTeste().imprimir('Cupom 002');
}

$ dart run interface_ok.dart
[impressora] Cupom 001
[teste] Cupom 002

base class: de fora, só extends

O Funcionario é uma base class: outro arquivo pode estender (e aproveitar o código), mas não implementar. A garantia é que todo "funcionário" passou de verdade pelo construtor e pelo código da mãe. E a filha tem de repetir um dos modificadores (base, final ou sealed):

import 'banco.dart';

base class Caixa extends Funcionario {
  Caixa(super.nome);

  @override
  String cracha() => '${super.cracha()} (caixa)';
}

void main() {
  print(Caixa('Bia').cracha());
}

$ dart run base_ok.dart
Funcionário: Bia (caixa)

Formas diferentes de fazer: qual escolher

SituaçãoQual usar
Uma classe comum, sem regras especiais (o caso mais comum em programas pequenos)class
Uma família fechada de tipos, cada um com dados próprios, tratada com switchsealed class
Opções fixas sem dados diferentes entre sienum (aula Enums)
A classe tem regras internas que ninguém pode driblarfinal class
Uma lista de métodos para os outros implementareminterface class ou abstract interface class
Outros podem herdar o código, mas ninguém pode "fingir" ser a classebase class
Código pronto para várias classesmixin / mixin class (aula Mixins)

Em programas de um arquivo só, como a maioria deste guia, os modificadores quase não fazem diferença (tudo é "cozinha"), exceto o sealed, cujo switch completo vale em qualquer lugar. Eles brilham em pacotes usados por outras pessoas (aula Pacotes do pub.dev).

As duas são o espelho uma da outra. A interface class diz "de fora, só implements"; o extends foi recusado. A base class diz "de fora, só extends"; o implements foi recusado. Em todas essas mensagens, o padrão é o mesmo: can't be extended / implemented outside of its library because it's a(n) … class. Leia a última palavra: ela diz qual modificador está barrando.

Missão final: o boleto entra na família

Missão: o main já tem um Boleto(80.0, 3), mas a classe não existe. Na aba pagamentos.dart, crie class Boleto extends Pagamento com um campo final int dias. Depois rode: o Dart vai reclamar do switch no main.dart. Acrescente o caso que mostra Boleto: R$ 80.0, vence em 3 dias.

import 'pagamentos.dart';

String resumo(Pagamento p) {
  return switch (p) {
    Pix pix => 'Pix de R\$ ${pix.valor} para ${pix.chave}',
    Cartao c => 'Cartão: R\$ ${c.valor} em ${c.parcelas}x',
  };
}

void main() {
  final pagamentos = [
    Pix(25.0, 'ana@lojinha'),
    Cartao(120.0, 3),
    Boleto(80.0, 3),
  ];
  for (final p in pagamentos) {
    print(resumo(p));
  }
}

Resumo

  • Cada arquivo .dart é uma biblioteca. Os modificadores de classe (Dart 3.0+) restringem o que outros arquivos podem fazer.
  • sealed: família fechada, filhas só no mesmo arquivo, e o switch sem _ confere se todas foram tratadas.
  • final: de fora, ninguém estende nem implementa. interface: de fora, só implementa. base: de fora, só estende.
  • A filha de uma classe base ou final tem de ser base, final ou sealed, mesmo no mesmo arquivo.
  • Nas mensagens can't be extended/implemented outside of its library because it's a … class, a última palavra diz qual modificador barrou.
