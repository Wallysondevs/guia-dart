Dart @override

Na aula Herança, a Bebida herdou o método descricao() do Produto, e o suco se descrevia igualzinho ao pão: Suco de laranja: R$ 6.50. Mas a Ana queria que a bebida mostrasse também o volume. Para isso, a subclasse escreve a sua própria versão do método, que passa a valer no lugar da herdada. Isso se chama sobrescrever o método (em inglês, override, "passar por cima").

Você vai aprender
  • Como sobrescrever um método herdado e para que serve a marca @override.
  • Como reaproveitar a versão da mãe com super.descricao().
  • O que acontece numa lista com objetos de várias classes: cada um usa a sua versão (polimorfismo).
  • Como sobrescrever o toString(), herdado de Object, para o print mostrar algo útil.
  • As regras da versão nova (mesmo tipo de retorno, mesmos parâmetros) e os erros reais quando elas são quebradas, incluindo o Stack Overflow.

Todos os programas desta aula rodaram no Dart 3.13.5 da máquina da Ana (usuária ana, computador notebook), com dart run arquivo.dart. Todos começam com a mesma classe Produto:

class Produto {
  String nome;
  double preco;

  Produto(this.nome, this.preco);

  String descricao() => '$nome: R\$ ${preco.toStringAsFixed(2)}';
}

Ela ocupa as linhas 1 a 8 de cada arquivo (mais uma linha em branco), por isso as mensagens de erro desta aula apontam linhas a partir da 10.

A ideia: a mesma ordem, cada um do seu jeito

Na padaria, a dona diz para todo funcionário: "apresente o produto ao cliente". O atendente do balcão diz o nome e o preço. O atendente das bebidas diz o nome, o preço e o tamanho do copo. O atendente das promoções diz o preço antigo e o novo. A ordem é a mesma para todos; o jeito de cumpri-la muda conforme quem a recebe.

No Dart, a ordem é o nome do método (descricao()), e cada classe pode ter o seu jeito de cumpri-la. Quem chama não precisa saber qual é a classe: só chama item.descricao().

1. Sobrescrevendo um método

class Bebida extends Produto {
  int volumeMl;

  Bebida(super.nome, super.preco, this.volumeMl);

  @override
  String descricao() => '$nome ($volumeMl ml): R\$ ${preco.toStringAsFixed(2)}';
}

void main() {
  final pao = Produto('Pão francês', 0.75);
  final suco = Bebida('Suco de laranja', 6.5, 300);
  print(pao.descricao());
  print(suco.descricao());
}
@override
Uma anotação (as que começam com @): um bilhete para o Dart e para quem lê dizendo "o método abaixo substitui um que veio da mãe". Ela não muda o que o programa faz; ela confere que você está mesmo sobrescrevendo algo (seção 5).
String descricao()
O mesmo nome, o mesmo tipo de retorno (String) e os mesmos parâmetros (nenhum) do método da mãe. Só o corpo muda.
=> '$nome ($volumeMl ml): …'
O jeito da bebida: nome, volume e preço. Ela usa os campos herdados (nome, preco) e o próprio (volumeMl).
$ dart run sobrescrever.dart
Pão francês: R$ 0.75
Suco de laranja (300 ml): R$ 6.50

O pão continua com a versão da mãe. O suco usou a versão nova. A versão do Produto não sumiu nem mudou: ela só deixou de valer para as bebidas.

2. Aproveitando a versão da mãe: super.descricao()

Repare que a bebida repetiu o pedaço R\$ ${preco.toStringAsFixed(2)}, que já estava no Produto. Se um dia a Ana mudar o jeito de mostrar o preço, vai ter de mudar nos dois lugares. Melhor: pedir à mãe a parte dela e só acrescentar o volume.

class Bebida extends Produto {
  int volumeMl;

  Bebida(super.nome, super.preco, this.volumeMl);

  @override
  String descricao() => '${super.descricao()} ($volumeMl ml)';
}

void main() {
  final suco = Bebida('Suco de laranja', 6.5, 300);
  print(suco.descricao());
}

$ dart run com_super.dart
Suco de laranja: R$ 6.50 (300 ml)

super.descricao() quer dizer "a descricao() da mãe". Ela devolveu Suco de laranja: R$ 6.50, e a bebida juntou (300 ml) no fim. É o padrão mais comum: a filha faz o que a mãe faz, e mais um pouco.

Sem o super., o método chama a si mesmo

Dentro da Bebida, escrever só descricao() chama a versão da própria bebida, que chama de novo, e de novo… até o programa estourar. Esse erro está em Quando dá errado.

3. Uma lista, três jeitos (polimorfismo)

Agora a vitrine da lojinha tem pão, bebida e um bolo em promoção. A promoção também sobrescreve a descricao(), com um corpo de várias linhas:

class Bebida extends Produto {
  int volumeMl;

  Bebida(super.nome, super.preco, this.volumeMl);

  @override
  String descricao() => '${super.descricao()} ($volumeMl ml)';
}

class Promocao extends Produto {
  double desconto;

  Promocao(super.nome, super.preco, this.desconto);

  @override
  String descricao() {
    final novo = preco * (1 - desconto);
    return '$nome: de R\$ ${preco.toStringAsFixed(2)} por R\$ ${novo.toStringAsFixed(2)}';
  }
}

void main() {
  final List<Produto> vitrine = [
    Produto('Pão francês', 0.75),
    Bebida('Suco de laranja', 6.5, 300),
    Promocao('Bolo de cenoura', 20.0, 0.25),
  ];

  for (final item in vitrine) {
    print(item.descricao());
  }
}

$ dart run lista.dart
Pão francês: R$ 0.75
Suco de laranja: R$ 6.50 (300 ml)
Bolo de cenoura: de R$ 20.00 por R$ 15.00

O laço tem uma linha, print(item.descricao()), e a variável item é do tipo Produto. Mesmo assim, cada objeto respondeu do seu jeito. Quem decide qual versão roda é o objeto de verdade (o que foi criado com Bebida(…) ou Promocao(…)), e não o tipo da variável. Esse comportamento tem um nome comprido, polimorfismo ("muitas formas"), e é o grande motivo de existir o @override: o código que percorre a vitrine não precisa de um if para cada tipo de produto.

Experimente: acrescente na vitrine uma Bebida('Café', 4.0, 50) e uma Promocao('Sonho', 6.0, 0.5). Depois apague o @override da Promocao e rode de novo: muda alguma coisa na saída?

4. Sobrescrevendo o toString()

Toda classe herda de Object (veja Herança), e Object tem um método toString(), que diz como o objeto vira texto. O print e a interpolação ('$suco') usam esse método. A versão de Object é pouco útil; sobrescrevendo, fica clara:

class Bebida extends Produto {
  int volumeMl;

  Bebida(super.nome, super.preco, this.volumeMl);

  @override
  String toString() => 'Bebida($nome, $volumeMl ml)';
}

void main() {
  final pao = Produto('Pão francês', 0.75);
  final suco = Bebida('Suco de laranja', 6.5, 300);
  print(pao);
  print(suco);
  print('No carrinho: $suco');
}

$ dart run tostring.dart
Instance of 'Produto'
Bebida(Suco de laranja, 300 ml)
No carrinho: Bebida(Suco de laranja, 300 ml)

O pão usou a versão de Object: Instance of 'Produto' ("uma instância de Produto"), que não diz qual produto é. O suco usou a versão nova. A aula toString, == e hashCode aprofunda esse método e os outros dois que vêm de Object.

5. Para que serve a marca @override

Se você tirar o @override, o programa roda igual: o Dart sobrescreve pelo nome do método, com ou sem a marca. Este arquivo é o com_super.dart sem a anotação:

$ dart run sem_override.dart
Suco de laranja: R$ 6.50 (300 ml)

Então por que escrever? Porque ela pega erros de digitação. Veja a Ana escrevendo descrisao (com "s") em vez de descricao:

class Bebida extends Produto {
  int volumeMl;

  Bebida(super.nome, super.preco, this.volumeMl);

  @override
  String descrisao() => '${super.descricao()} ($volumeMl ml)';
}

void main() {
  print(Bebida('Suco de laranja', 6.5, 300).descricao());
}

$ dart run erro_nome.dart
Suco de laranja: R$ 6.50
$ dart analyze erro_nome.dart
Analyzing erro_nome.dart...

warning - erro_nome.dart:16:10 - The method doesn't override an inherited method. Try updating this class to match the superclass, or removing the override annotation. - override_on_non_overriding_member

1 issue found.
  • O dart run não reclamou: para ele, descrisao é só um método novo da bebida. E a saída saiu sem o volume, porque o main chamou descricao() e caiu na versão da mãe. Um erro silencioso.
  • O dart analyze (o "analisador", que lê o código procurando problemas; veja Análise e Formatação) avisou: warning ("aviso") na linha 16, coluna 10: "o método não sobrescreve um método herdado. Ajuste a classe para combinar com a superclasse, ou remova a anotação". O nome no fim, override_on_non_overriding_member, é o código do aviso.

É o @override que torna esse aviso possível: sem a marca, o analisador não teria como saber que você queria sobrescrever. Os editores de código (VS Code, Android Studio) mostram esse aviso enquanto você digita. Por isso o guia de estilo do Dart pede: sempre escreva @override ao sobrescrever (o lint annotate_overrides).

O método novo pede um parâmetro a mais

  int volumeMl;

  Bebida(super.nome, super.preco, this.volumeMl);

      comVolume ? '${super.descricao()} ($volumeMl ml)' : super.descricao();
}

Resumo

  • Sobrescrever é escrever na subclasse um método com o mesmo nome de um herdado; a versão nova vale para os objetos da subclasse.
  • Marque sempre com @override: o programa roda igual, mas o analisador passa a pegar erros de digitação.
  • super.metodo() chama a versão da mãe: a filha faz o mesmo e mais um pouco. Sem o super., o método chama a si mesmo e acaba em Stack Overflow.
  • Quem decide a versão é o objeto de verdade, não o tipo da variável (polimorfismo): uma List<Produto> com bebidas e promoções se descreve sem nenhum if.
  • A versão nova mantém o tipo de retorno e não pode exigir parâmetros a mais; senão, erro de compilação com um Context: apontando a versão da mãe.
  • Sobrescreva o toString() para o print mostrar algo melhor que Instance of '…'.
