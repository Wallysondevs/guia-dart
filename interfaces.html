Dart Interfaces (implements)

A Ana comprou uma impressora de etiquetas para a lojinha. Ela quer imprimir etiquetas de produtos (para a prateleira) e de clientes (para as encomendas). Produto e cliente não têm nada a ver um com o outro: um cliente não "é um" produto, então herança não serve. O que os dois têm em comum é só uma promessa: "eu sei gerar a minha etiqueta". No Dart, essa promessa se chama interface, e uma classe a assume com implements (em inglês, "implementa", "cumpre").

Você vai aprender
  • O que é uma interface: uma lista de métodos que a classe promete ter.
  • Como escrever class Produto implements Imprimivel e usar classes diferentes no mesmo lugar.
  • Como uma classe cumpre várias interfaces de uma vez.
  • Que, no Dart, toda classe também é uma interface, e para que isso serve (a balança de teste).
  • Como cumprir uma interface da própria linguagem, Comparable, para o sort() funcionar.
  • A diferença entre extends e implements, e os erros reais de cada engano.

Todos os programas desta aula rodaram no Dart 3.13.5 da máquina da Ana (usuária ana, computador notebook), com dart run arquivo.dart. Ajuda ter feito Classes Abstratas antes.

A ideia: a tomada

A tomada da parede é uma interface: ela diz "tudo o que tiver este formato de plugue pode ser ligado aqui". A tomada não quer saber se é um liquidificador, um carregador ou um abajur, nem como cada um funciona por dentro. Basta cumprir o formato.

  • A interface é o formato do plugue: os nomes dos métodos, seus parâmetros e o que devolvem.
  • Cada classe que implementa é um aparelho: escreve por conta própria o que acontece quando é ligado.
  • O código que usa a interface é a tomada: funciona com qualquer aparelho que cumpra o formato.

A diferença para a herança: com extends, a filha recebe o código da mãe. Com implements, a classe não recebe nada; ela só promete, e escreve tudo sozinha.

1. A primeira interface

O Dart não tem uma palavra separada para "interface" no sentido mais simples: o costume é escrever uma classe abstrata só com métodos abstratos e usá-la com implements.

abstract class Imprimivel {
  String etiqueta();
}

class Produto implements Imprimivel {
  final String nome;
  final double preco;

  Produto(this.nome, this.preco);

  @override
  String etiqueta() => '[PRODUTO] $nome - R\$ ${preco.toStringAsFixed(2)}';
}

class Cliente implements Imprimivel {
  final String nome;
  final String telefone;

  Cliente(this.nome, this.telefone);

  @override
  String etiqueta() => '[CLIENTE] $nome - tel. $telefone';
}

void imprimirTodas(List<Imprimivel> coisas) {
  for (final c in coisas) {
    print(c.etiqueta());
  }
}

void main() {
  imprimirTodas([
    Produto('Pão de queijo', 1.5),
    Cliente('Bia', '99999-1234'),
    Produto('Café coado', 4.0),
  ]);
}
abstract class Imprimivel { String etiqueta(); }
A interface: "quem for imprimível tem um método etiqueta() que devolve String". O nome termina em -ível de propósito: descreve uma capacidade ("pode ser impresso"), não uma coisa.
class Produto implements Imprimivel
"Produto cumpre a promessa de Imprimivel." A partir daqui, o Dart exige que Produto tenha etiqueta().
@override String etiqueta() => …
O método prometido, com o jeito do produto. Usa-se o mesmo @override da herança.
class Cliente implements Imprimivel
Outra classe, sem parentesco nenhum com Produto, cumprindo a mesma promessa.
void imprimirTodas(List<Imprimivel> coisas)
A "tomada": a função aceita qualquer lista de imprimíveis. Ela só pode chamar o que a interface garante (etiqueta()); c.preco ali daria erro, porque cliente não tem preço.
$ dart run etiquetas.dart
[PRODUTO] Pão de queijo - R$ 1.50
[CLIENTE] Bia - tel. 99999-1234
[PRODUTO] Café coado - R$ 4.00

Na mesma lista, produtos e um cliente; cada um gerou a etiqueta do seu jeito. Amanhã, se a Ana quiser etiquetas de fornecedores, basta uma classe nova que implements Imprimivel: a função imprimirTodas não muda (é a missão final).

2. Várias interfaces na mesma classe

Uma classe só pode ter uma mãe no extends, mas pode cumprir quantas interfaces quiser, separadas por vírgula. O produto, além de imprimível, agora sabe virar uma linha de planilha (CSV, o formato de texto com campos separados por ;):

abstract class Imprimivel {
  String etiqueta();
}

abstract class Exportavel {
  String paraCsv();
}

class Produto implements Imprimivel, Exportavel {
  final String nome;
  final double preco;

  Produto(this.nome, this.preco);

  @override
  String etiqueta() => '[PRODUTO] $nome - R\$ ${preco.toStringAsFixed(2)}';

  @override
  String paraCsv() => '$nome;$preco';
}

void main() {
  final p = Produto('Pão de queijo', 1.5);
  print(p.etiqueta());
  print(p.paraCsv());
  print(p is Imprimivel);
  print(p is Exportavel);
}

$ dart run duas.dart
[PRODUTO] Pão de queijo - R$ 1.50
Pão de queijo;1.5
true
true

O produto agora "é" as duas coisas: o is responde true para as duas interfaces. Ele pode entrar numa List<Imprimivel> e também numa List<Exportavel>. Dá para juntar com herança também: class Bebida extends Produto implements Exportavel (o extends vem primeiro).

Experimente: faça o Cliente da seção 1 também implementar Exportavel (com paraCsv() devolvendo '$nome;$telefone'). Antes de escrever o método, rode e leia o que o Dart reclama.

  print(bia.etiqueta());
}

3. Toda classe é uma interface

No Dart, qualquer classe pode aparecer depois do implements, mesmo uma classe comum, com código dentro. Isso é chamado de interface implícita: toda classe "publica" o seu formato de plugue. Para que serve? Um exemplo clássico é o teste. A lojinha tem uma balança ligada ao computador; para testar o programa sem a balança, a Ana cria uma balança "de mentira" com o mesmo formato:

class Balanca {
  double pesar() {
    print('Pesando na balança de verdade...');
    return 0.350;
  }
}

class BalancaDeTeste implements Balanca {
  @override
  double pesar() => 1.0;
}

void venderQueijo(Balanca balanca) {
  final kg = balanca.pesar();
  print('Queijo: ${kg.toStringAsFixed(3)} kg = R\$ ${(kg * 60).toStringAsFixed(2)}');
}

void main() {
  venderQueijo(Balanca());
  venderQueijo(BalancaDeTeste());
}

$ dart run classe_comum.dart
Pesando na balança de verdade...
Queijo: 0.350 kg = R$ 21.00
Queijo: 1.000 kg = R$ 60.00

A BalancaDeTeste não herdou nada (por isso não apareceu "Pesando na balança de verdade..." na segunda venda): ela só tem o mesmo formato. A função venderQueijo aceita as duas, e o teste sempre pesa exatamente 1 kg, o que facilita conferir a conta. A aula Testes usa essa ideia.

Implementar uma classe com campos dá trabalho

Quando a classe implementada tem campos, eles também fazem parte do formato, e você tem de declará-los de novo. O erro que aparece quando você esquece está em Quando dá errado. Se você quer proibir que outros implementem (ou estendam) uma classe sua, existem modificadores para isso (aula sealed, final, base e interface).

4. Uma interface da própria linguagem: Comparable

A biblioteca do Dart também tem interfaces. Comparable ("comparável") promete um método compareTo, que diz se um objeto vem antes ou depois de outro. É ele que o sort() de uma lista usa para ordenar (veja Métodos de Lista). Números e textos já são Comparable; os seus produtos, não, até você implementar:

class Produto implements Comparable<Produto> {
  final String nome;
  final double preco;

  Produto(this.nome, this.preco);

  @override
  int compareTo(Produto outro) => preco.compareTo(outro.preco);
}

void main() {
  final vitrine = [
    Produto('Bolo', 20.0),
    Produto('Pão francês', 0.75),
    Produto('Suco', 6.5),
  ];
  vitrine.sort();
  for (final p in vitrine) {
    print('${p.nome}: ${p.preco}');
  }
}
implements Comparable<Produto>
"Produto é comparável com outro Produto." O <Produto> diz com quem a comparação é feita (veja Genéricos).
int compareTo(Produto outro)
O método prometido. A regra: devolver um número negativo se este produto vem antes, zero se empata, positivo se vem depois.
preco.compareTo(outro.preco)
O double já sabe se comparar; o produto só repassa a pergunta para os preços. Resultado: ordem do mais barato para o mais caro.
$ dart run comparable.dart
Pão francês: 0.75
Suco: 6.5
Bolo: 20.0

Missão final: etiqueta de fornecedor

Missão: o programa não compila, porque o Fornecedor não prometeu ser Imprimivel. Faça a classe implementar a interface (não esqueça o @override) e rode até aparecer [FORNECEDOR] Laticínios Serra junto com as outras etiquetas. A função imprimirTodas não precisa mudar.

  String etiqueta();
}

class Produto implements Imprimivel {

  final double preco;

  Produto(this.nome, this.preco);

  @override
  String etiqueta() => '[PRODUTO] $nome - R\$ ${preco.toStringAsFixed(2)}';
}

class Fornecedor {

  Fornecedor(this.nome);

  for (final c in coisas) {
    print(c.etiqueta());
  }
}

void main() {
  imprimirTodas([
    Produto('Queijo minas', 32.0),
    Fornecedor('Laticínios Serra'),
  ]);
}

Resumo

  • Uma interface é uma promessa de métodos; implements assume a promessa e o Dart exige que todos os membros sejam escritos.
  • O costume é usar uma abstract class só com métodos abstratos como interface; mas qualquer classe serve (interface implícita), inclusive para criar versões de teste.
  • Uma classe tem uma mãe só (extends), mas pode implementar várias interfaces (implements A, B).
  • implements não traz código: nada de super.metodo(), e os campos da classe implementada também têm de ser declarados.
  • O Dart não aceita "parecido": sem implements, um objeto com o mesmo método não vale como a interface.
  • implements Comparable<T> com compareTo permite lista.sort(); sem isso, o sort() estoura durante a execução. No stack trace, procure a primeira linha com o seu arquivo.
